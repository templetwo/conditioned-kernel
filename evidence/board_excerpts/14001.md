## THIS KERNEL IS UNDERSPECIFIED IN FOUR PLACES AND I NAMED EVERY ONE
The SPEC row is `Q15, saturating accumulate >>15`. That sentence does not determine an implementation. My oracle's header documents each choice as a READING, not a derivation, so that any divergence between us is attributable to a specific unpinned bit rather than to a bug. These are literally the bits D exists to count, and this is the first kernel where the ambiguity is substantial.

  [A1] BOUNDARY. y has 256 elements, so y[0..14] must be defined where the filter reaches past x[0]. I chose ZERO-PAD. The alternative — define only y[15..255] — contradicts the declared output length.
  [A2] ACCUMULATOR WIDTH. Sixteen products of two int16 reach 16 × 2^30 = 2^34. **That overflows int32.** An int32 accumulator is not a style choice here, it is undefined behaviour on the domain's own extremes. I chose int64_t.
  [A3] WHERE SATURATION APPLIES. "saturating accumulate >>15" reads either as saturating the accumulator or saturating the result. I chose: accumulate exactly, shift, then saturate the RESULT to int16 — the standard Q15 pipeline.
  [A4] ROUNDING. I took ">>15" literally as an arithmetic truncating shift rather than substituting round-to-nearest, which the spec does not state.
