## THE ROOT CAUSE OF #9938, FOUND AND PROVEN
#9938 said granite4:350m (708MB) OOM'd on an 8GB board after gemma3:4b and called it async VRAM release. That was DIRECTIONALLY right and MECHANISTICALLY incomplete. The real mechanism, reproduced live today on a freshly-booted device:

OLLAMA'S ADMISSION CONTROL TRUSTS A NUMBER CUDA CANNOT HONOR.
Ollama's scheduler logged: available="5.8 GiB" free="6.3 GiB" and admitted the load. cudaMalloc then failed. At that moment the REAL numbers were:
  MemFree:      ~1.8 GB      <-- what CUDA can actually get
  MemAvailable: ~6.7 GB      <-- what ollama believed
  Cached:       ~5.0 GB      <-- page cache, counted as "available", NOT reclaimable by CUDA
On Tegra, unified-memory allocation does NOT trigger page-cache reclaim. So MemAvailable is a LIE for this purpose. Ollama admits, the runner spawns, cudaMalloc fails, the runner dies, HTTP 500 comes back, and it reads as "the model is broken."

PROOF, controlled:
  MemFree 1.8 GB  -> qwen2.5-coder:3b load FAILS (cudaMalloc OOM), repeatedly.
  Force page-cache reclaim (fault in anonymous pages, then release, no root needed)
  MemFree 4.3 GB  -> SAME model loads in 3.8s, responds "ok", 100% GPU.
Nothing else changed. That is the whole finding.

## WHAT THIS CORRECTS IN SPEC §4a (my own text, written this morning)
§4a says: "poll free memory until it exceeds incoming_model_size + headroom."
TWO ERRORS IN THAT SENTENCE, both mine:
[1] "free memory" is ambiguous and my first implementation used MemAvailable. MemAvailable reported 6.7 GB while the load failed. THE BARRIER MUST POLL MemFree. Page cache must be actively reclaimed, not counted.
[2] "incoming_model_size" is wrong. Download size understates reality badly, and even RESIDENT size understates the TRANSIENT allocation during load. Measured on this device:
      qwen2.5-coder:3b  download 1.9 GB  resident 2280 MB  needs ~3600 MB MemFree to load
      granite4:micro    download 2.1 GB  resident 2586 MB  needs ~5100 MB MemFree to load
  granite needs ~5 GB free to land a 2.6 GB model. Transient load overhead is nearly 2x resident. These thresholds are EMPIRICAL, per model, and must be measured at bring-up, not derived from any published size.

## I ALMOST REPEATED #9938'S EXACT MISTAKE
granite4:micro FAILED its smoke test twice. Both times the barrier had let it proceed with insufficient MemFree (4149 MB, then 4693 MB, against a real need of ~5100 MB). Given a clean 5231 MB it generated correct C immediately.
Had I recorded those as generator failures, I would have written a second false negative against the Granite family, for the second time in this project, for the same underlying reason. The tell was identical to the one #9938 named: a control behaving impossibly. I caught it only because #9938 taught me to distrust exactly that shape.
MY BARRIER WAS THE BUG: it reclaimed toward a target, missed the target, and PROCEEDED ANYWAY. A barrier that does not fail closed is not a barrier. Corrected: barrier_ok is now required before any load; when false the result is an INFRA FAULT that is not scored, does not consume a sample, and does not enter the repair budget. That is SPEC §9's rule, and I had violated it in my own first implementation of it.

## REQUIRED §4a AMENDMENT (proposed, for Anthony/Grok to counter)
  1. Poll MemFree, never MemAvailable. Record BOTH in the receipt so the gap stays visible.
  2. Per-model memfree_needed_mb, empirically measured at P0, stored in the receipt.
  3. Reclaim page cache before load. Root-free method: fault in anonymous pages to MemAvailable-500, release. Iterate up to N times toward target. (Cleaner alternative if Anthony extends sudoers: `sync; echo 3 > /proc/sys/vm/drop_caches`.)
  4. FAIL CLOSED. barrier_ok false = infra fault = not scored, never a candidate failure.
  5. Receipt carries: evict_ms, ps_empty, reclaim_ms, reclaimed, need_mb, memfree_before_load_mb, memavailable_mb, barrier_ok.
