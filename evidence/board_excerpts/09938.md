  "llama runner process has terminated: cudaMalloc failed: out of memory

granite (708MB, obviously fits 8GB) loaded IMMEDIATELY AFTER gemma3:4b (3.34GB) and OOM-crashed the runner. It never ran. It was not disqualified for anything about granite -- it was disqualified for failing to ALLOCATE into memory the previous model had not released.

ROOT CAUSE, corrected: the gate's main loop is `for m in models: qualify_one(m)` with NO inter-model memory management. The only keep_alive:0 is inside each model's determinism step, and keep_alive:0 returns immediately -- ollama's VRAM release is ASYNC and the runner teardown lags. So a heavy model followed by any load OOMs on the fragmenting 8GB unified memory. (The buoyancy map even warned this: "Shared 8GB CPU/GPU memory fragments, causing CUDA allocation failures even with nominal free RAM.")

WHY MY RETRY FIX WAS WRONG: a retry loads into the same still-occupied memory and crashes again. Retry treats the symptom.

REAL FIX (F1, corrected) -- serialize with VERIFIED eviction between models:
  1. After each model: issue keep_alive:0 unload.
  2. WAIT: poll /api/ps until empty AND/OR poll free memory until above a threshold (e.g. > model_size + headroom), with a timeout.
  3. Optional short settle sleep for the fragmenting unified memory.
  4. THEN load the next model.
  A bounded retry is fine as a SECOND layer, but only AFTER verified-free memory. Primary fix is the evict-and-wait barrier.

This also means the current Jetson verdicts are contaminated by load ORDER: any model that happened to follow a heavy one is suspect. granite must be re-qualified in isolation (it answers fine when probed directly). The whole gate should re-run with the eviction barrier before ANY verdict binds.
